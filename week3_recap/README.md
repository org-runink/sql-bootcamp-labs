# Week 3 recap — three sheets, one idea

> Folders elsewhere in this repo are named by position in the course. This one
> is not a class — it is a **recap**, sized to drop into whichever sessions
> follow week 3.

Nothing in these three sheets is new. Every idea appeared somewhere in week 3 —
but it appeared on four different days, against four different datasets, and
students meet each one as a local trick rather than as the same recurring
mechanism.

These sheets put all of them on **one dataset**, so the pattern is visible.

```
exercises/       sheets 01–03, thirty questions
exercises/data/bronze/   the superstore landing zone from day 1
solutions/       the answers, with the real output quoted
```

## Why these three

Not chosen by feel. Week 3's own worksheets end on **deliberate errors**, and the
class READMEs document them; those tables are a record of what each day judged
hard enough to teach by making it fail. Three mechanisms recur across days:

**Grain and fan-out** produced four of them:

| Day | Error |
|---|---|
| day 1, ws16 | `MergeError: not a one-to-one merge` |
| day 4, ws02 | `ValueError: Index contains duplicate entries` |
| day 4, ws04 | `MergeError: not a one-to-one merge` |
| day 4, ws07 | `AssertionError: fact table has 2219 rows` |

**Rows disappearing** produced day 4 ws06 (`net_tuition has 1216 nulls`), day 4
ws07's missing 156, day 3 ws03's 21,117 unmatched rows, and day 1 ws14's
`groupby`.

**Averaging what should be summed** produced day 2 ws05's `1995.2` against
`1522.22`, and day 4 ws03's `0.0875` against `0.0835`.

All three are one instruction: **the dangerous results are the ones that do not
raise**, so the checks have to be things you decide to run.

## The data

`exercises/data/bronze/` is the same superstore landing zone as
`week3_day1_afternoon` — deliberately, so students spend their attention on the
concept rather than on a new schema. Generated by
[`scripts/generate_medallion_data.py`](../scripts/generate_medallion_data.py).

Real properties the sheets teach from: `orders` at line grain (8,060 rows for
5,361 orders), `returns` keyed by `OrderID` (558 rows → 837 lines), 20 customers
who never ordered, and a re-delivery of 40 rows.

**Sheet 02 introduces two gaps the real data does not have**, because real CRM
exports do: 62 customers lose their segment, 26 order lines lose their product.
Both are deterministic (every 30th and every 320th row), stated in the setup
cell, and every number in the solutions is reproducible from them.

## What the sheets find

| Finding | Where |
|---|---|
| `LineID` not unique — 40 re-delivered rows, **62,694.27 (0.462%)** of phantom revenue | 01 Q2 |
| `validate="many_to_one"` **passes** on the returns join, and the join is still a trap | 01 Q3-Q4 |
| 558 returns → **837 rows**; the count overstates by **50%** | 01 Q5 |
| ...and `SUM(Sales)` is **identical either way** — 1,485,707.73 | 01 Q6 |
| `groupby` on a null key reports **7,837 of 8,060** rows, silently | 02 Q1-Q2 |
| An inner join on a null key deletes **26 rows** and **46,101.51 (0.340%)** | 02 Q5 |
| A trailing space makes a filter return **0** where 1,902 rows match | 02 Q7 |
| **`'Prarie'`** — a real misspelling in the source data, found by a 6-line check | 02 Q8 |
| Average of averages: **1687.72 vs 1683.72**, from a **25x** group-size ratio | 03 Q1-Q2 |
| Return rate by segment: **0.1628 vs 0.1154** for Small Business, both defensible | 03 Q3-Q4 |
| Ranking by rate puts a **32-line** group in the top five | 03 Q5 |
| Rounding before summing costs **8 cents**; rows vs footer **2 cents** | 03 Q8 |
| `SUM(Discount)` is **400.36** — a real number, and meaningless | 03 Q9 |

Sheet 02 question 8 is the one to point at in class. The check is six lines —
`repr()` the distinct values of every low-cardinality text column — and it found
a genuine defect nobody had noticed in the source data.

## Some cells are supposed to fail

One per sheet, always the last question.

| Sheet | Raises | Why |
|---|---|---|
| 01 | `MergeError: not a one-to-one merge` | `orders` is the side that breaks it, not `returns` |
| 02 | `AssertionError: the segment report accounts for 7837 of 8060 rows` | the only thing on the sheet that objected |
| 03 | `AssertionError: the average of 8 regional averages is 1687.72...` | if adding a tiny group would move your headline, you are using the wrong average |

## Two answers that are not the expected ones

Worth flagging, because both were surprises when the sheets were built and both
teach more than the version that was planned:

**Sheet 01 Q6.** The returns join fans out, so the instinct is that every number
from it is suspect. `SUM(Sales)` is *exactly right* — a fan-out damages a measure
only if the measure comes from the side that fanned out. Same join, correct sum,
wrong count.

**Sheet 03 Q7.** Day 1 worksheet 12 found the same column summing to
`1605576.2175` one way and `1605576.2174999998` another. On **this** data all
five summation methods agree exactly, including `math.fsum`. The lesson is
therefore not "floats are unreliable, look" but that whether reordering matters
is a property of the *data*, not the code — which is exactly why `==` on floats
is a rule and not a judgement call.

## Verification

All three solutions were executed in the lab image with
`jupyter nbconvert --to notebook --execute --allow-errors`. **Exactly three cells
errored** — one per sheet, each the intended final question.

**172 distinct numeric literals** quoted in the solutions were matched against
that execution. 20 of them are citations of earlier week-3 worksheets
(*"day 2 worksheet 05 found..."*); those are checked against the prose of the
worksheet they cite, not accepted on trust.

That check caught a real error: this recap originally cited day 2's figure as
`1995.20`, and day 2's notebook prints `1995.2`. The trailing zero was wrong in
`week3_day2_afternoon/README.md` too, and has been corrected there.

Verified against **pandas 3.0.5** on Python 3.13.15.
