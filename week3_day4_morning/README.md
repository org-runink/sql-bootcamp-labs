# Week 3, day 4 (morning) — Data modeling and ELT design

The L03 lecture *Data Modeling and ETL Design* works one case study end to end:
an education provider's **enrollment** process, taken from the operational schema
on slide 24 to the star schema on slide 29, then through a seven-step ELT design.

These eleven worksheets build that model. Not describe it — **build it**, on real
data, one lecture step per sheet, ending with a fact table that passes seven
quality checks and answers five of the six business questions the lecture set.

The sixth needs a table that does not exist, which is worksheet 10's last
question and the most useful failure in the folder.

## The data

`exercises/data/` holds twelve CSVs matching slide 24's ER diagram exactly —
table names, column names and all:

```
students   city        enrollment   transaction    payment_type
course     program     category     discount_type  cohort

```

7,973 rows, generated by [`scripts/generate_enrollment_data.py`](../scripts/generate_enrollment_data.py)
with a fixed seed, so it is byte-identical every run:

```bash
python3 scripts/generate_enrollment_data.py            # rewrite the CSVs
python3 scripts/generate_enrollment_data.py --verify   # check, write nothing
```

**Everything wrong with it is planted, and every defect is one the deck names.**
An operational database that is already clean teaches nothing about Step 3 or
Step 7:

| What | Size | Lecture |
|---|---|---|

| `discount_type.discount_amount` is null for one promotion | 197 enrollments | slide 36, *default missing discount amount* |
| `category.category_name` is null | 316 enrollments | slide 36, *standardize missing program category* |
| `enrollment.status = 'cancelled'` | 117 rows | slide 36, *apply reporting rule* |

| `TEST` students with their own enrollments | 6 students, 18 rows | slide 35, *filter test records* |
| enrollments with no transaction at all | 157 rows | inner vs left join |
| `transaction` is at **payment** grain, not enrollment grain | 4,856 rows, 2,243 enrollments | slide 28's footnote — the reason Step 4 exists |

## Some cells are supposed to fail

Ten — the last question of every coded sheet, so Restart & Run All reaches the
bottom before anything raises.

| Sheet | Raises | Why it is there |
|---|---|---|
| 01 | `KeyError: 'program_id'` | the source will not let you join enrollment straight to program |
| 02 | `ValueError: Index contains duplicate entries` | `pivot` is the only operation that checks the grain claim |
| 03 | `TypeError: Cannot perform reduction 'mean' with string dtype` | the type system catches the silly version of this error and none of the serious ones |
| 04 | `MergeError: not a one-to-one merge` | `validate=` checks the assumption before producing a row |
| 05 | `KeyError: None of [10, 20, ...] are in the index` | loading facts before dimensions |
| 06 | `AssertionError: net_tuition has 1216 nulls` | the arithmetic ran fine and skipped 54% of the business |
| 07 | `AssertionError: fact table has 2219 rows` | an inner join, and a table that passes every internal check |
| 08 | `MergeError: not a many-to-one merge` | a duplicated dimension key |
| 09 | `AssertionError: 7 fact rows have an unresolved student_id` | no `Unknown` member to point at |
| 10 | `KeyError: 'payment_type_key'` | the model's edge — and the case for a galaxy schema |

Worksheet 06's is the one to sit with. The arithmetic **did not complain**: it
produced 1,216 nulls, `SUM` skipped every one, and returned a plausible revenue
figure computed over 46% of the business. Only the explicit assertion objected.

## The theme

Same one the SQL, Pandas and Snowflake sessions ran on: **the dangerous results
are the ones that do not raise.**

Here it arrives from the modelling side. A dimensional model is a place to make
decisions **once, at load time, in writing** — instead of leaving them to every
analyst, in every query, forever:

- the grain, tested rather than asserted
- `Unknown` instead of null, so 316 enrollments appear in a report instead of
  vanishing from it
- the numerator and denominator stored, the ratio derived
- one rule for cancellations, in a register that computes its own counts
- `Unknown` dimension members, so nothing is silently dropped by a join

And then the step everyone skips, which is slide 30: take the questions the model
was built for and actually ask them. Five work. The sixth does not, and finding
that out at design time costs five minutes.
